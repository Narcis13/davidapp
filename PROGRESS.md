## Decisions

- **Word times: whisper DTW anchors refined at pauses (speech agent).** whisper's own token times put only 42 % of word starts within 2 frames on a take with known times (up to 1 s off at sentence edges), short of the 95 % required. The studio now runs whisper with DTW token times (`-dtw <preset> -nfa`), takes one reliable time inside each word, and places each word boundary on the quiet stretch (≥ 40 ms) between two words, or between the anchors when there is none. Measured: 69/69 starts within 2 frames on the known-times take (its gaps help; said in the report), 26/26 sentence-edge words of natural speech against Kokoro's own sentence offsets. Inner words of continuous speech have no independent reference.
- **Provenance: unknown unless said (provenance agent).** A file asset added without a licence records it as unknown (uploads used to say "uploaded by the user", footage defaulted to "original"); only a final render (`final: true`) checks, so old journals, drafts and review renders are unaffected. Clips 9 and 10 pass `license: "original"` for the studio's own recordings. Narrations default to original and a voice with a model is flagged AI-generated.
- **Repo round trip (exchange agent, design by the lead).** A content store at the repo root, `library/` (`versions/<slug>@<n>.json`, `sources/`, `files/<sha256>.<ext>`), shared by every clip folder's `clip.json` (composition as saved, closure, files manifest, frame hashes). Import recreates each version with its exact number (sparse numbers allowed), compiles functions and refuses if they compile differently, re-bakes sequences from their recipe, and checks everything before writing. Files whose provenance says they may not be redistributed (an unknown licence counts) or over 50 MB stay out of git, named by SHA-256 with licence and source. Rows are recreated from the export, not re-validated: the export is the studio's own.
- **The machine.** As in iteration 3: the brief describes macOS 15.5 on an Intel i5 with 5.5 GB free; this session runs on the Windows 11 PC (i9-14900KF, 32 threads, 1.7 TB free, Node 24.19, FFmpeg 9.0.2). Baselines (hashes, speed) are taken here from a worktree of `0ea078c` sharing this checkout's `node_modules`. Caches are still bounded as the brief asks, and disk use is measured, as if the disk were small.

- **Footage: a shared decoder per process, frames from the server for the preview (D5).** Weighed:
  1. *Decode on demand in each render worker* (one FFmpeg per worker): simple, but the pool hands frames to whichever worker is idle, so each of N workers would decode nearly every frame (N× the decoding, N decoders' memory), and a seek per frame costs ~45 ms against ~2.5 ms decoding forward (measured on 640×360 H.264).
  2. *A frame cache on disk* (every frame decoded once at import, stored as images): random access is free, but the disk cost is every frame of every file (a 60 s 1080p recording is ~1,800 frames; as PNG ~2–4 GB, which the brief rules out; as JPEG ~300 MB and lossy, so the render would draw a degraded frame).
  3. **Chosen:** keep the file as it is; in each process one decoder per file (FFmpeg, decoding forward, restarted with a seek only for a jump), a byte-bounded memory cache of decoded RGBA frames (`STUDIO_FOOTAGE_CACHE_MB`, 512 MB default; at most 4 decoders, closed after 20 s idle); render workers ask the pool's thread for the frames a clip frame needs (as they load sequence frames) and get a copy over the message port. Which frame came out of a seek is read from its timestamp (`showinfo` with `-copyts`) and matched against the frame table, never assumed, so a seek that lands early or late cannot shift the picture: seeking to each frame of an H.264 file with B-frames, an MKV with a 2.5 s start offset, VP9 WebM and a rotated MP4 gives byte-identical frames to decoding in order (test). Colour conversion is explicit (the stream's matrix and range, unknown HD = BT.709, unknown SD = BT.601; bit-exact scaler flags), so a frame's RGBA is the same every time. Disk: the file itself plus a thumbnail, an 8-frame filmstrip and a waveform image.
  - Preview: *(a) decode in the browser* (WebCodecs needs a demuxer dependency for MP4/MOV/WebM, and its YUV→RGB conversion differs from FFmpeg's, so parity would depend on the GPU) vs **(b) frames from the server** (chosen): the preview worker fetches `/api/footage/<slug>/<v>/<index>.png` from the same service, so the preview draws the same source frame converted the same way; PNG when paused or scrubbing (exact), JPEG q90 while playing (fast; redrawn as PNG when it stops), with an immutable cache header and a 128 MB encoded-frame cache on the server.
  - The frame rule (`src/core/footage.js`, shared): clip time → the item's own time → source time (trim `in`/`out` with `out` exclusive, `speed`, `loop`, `hold`) → the last source frame at or before it (sample and hold, never blended), from the frame table read at import (every decoded frame's timestamp). Variable frame rate files work the same way. A footage frame placed 1:1 on whole pixels is copied without smoothing (Skia's high-quality filter softens even at 1:1, mean 0.4 levels); any other placement draws like an image.
  - Footage reaches function assets through `image` parameters (a browser frame, a camera): the asset gets the frame at its own time. Not as a parameter default (validation draws without footage), and not inside a precomp's `f.layers` (noted as a limit).
  - Its sound: the same ref on an audio track plays the file's audio through the mixer (any speed change is not applied to the sound: noted).
