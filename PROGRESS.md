## Decisions

- **Hash baseline on this machine** (macOS, Apple Color Emoji): `scripts/hashes.mjs` records, per showcase clip, the 18 sampled hashes of its first render and 120 dense frames (every 8th) drawn through MCP `frame_hashes`. Two builds from empty data dirs matched exactly. `docs/showcase/v2/reports/baseline-hashes.json`.
- **Speed baseline**: `scripts/speed.mjs`, three renders per clip on the iteration-1 code, median `renderSeconds`: clip 1 27.4 s, clip 2 30.1 s, clip 3 17.0 s (8 workers). Run-to-run spread is about ±15 % on this machine, so the final comparison uses more runs, interleaved, on a quiet machine. `reports/baseline-speed.json`.
- **Old shape = old code path.** Composition v2 is a superset of v1: every new field is optional. An item with none of them (no transform, keyframes, motions, effects, mask, transition, format override) is drawn by exactly the iteration-1 code, so old clips stay byte-identical. Anything new goes through a new path.
- **Transform model.** A visual item gets `transform: { space, x, y, width, height, anchorX, anchorY, scale, scaleX, scaleY, rotation }`. `space` is `frame` (default) or `safe`; x, y, width, height are fractions of that rectangle, so a layout means the same thing in every format. The item draws into a width×height box (that is its `f.width/f.height`; a full-frame box keeps the frame's safe zone), the box's anchor point sits at (x, y), and the box is scaled and rotated (degrees) about the anchor. Opacity and blend stay item fields. The legacy `box` is read as a transform with the same box. Drawing is a canvas transform, not a resample, so vectors stay sharp.
- **Per-format overrides**: `item.formats[vertical|horizontal|square] = { transform?, keyframes?, params?, hidden? }`, merged over the base (transform and params key by key). The composition's own format edits the base; the editor's other format tabs edit that format's override. Remix and `start_render { format }` render one composition in another format with that format's overrides.
- **Keyframes**: `item.keyframes[prop] = [{ t, v, ease }]` with item-local t. Props: the transform fields, `opacity`, and `params.<name>` for numeric and colour params. Easing names come from the `easing` asset family: the composition pins one (`composition.easing = "easing@1"`, added on first use), so a keyframe's curve is a library asset, versioned and traced like any other. Colours interpolate per channel in sRGB.
- **Layers**: tracks still draw bottom to top in array order. New edit ops `move_track { id, index }`, `move_item { id, track, index }`, `update_track { id, name, locked, hidden, solo, muted }`. Solo shows only soloed visual tracks; mute silences audio tracks.
- **Proposals are not drafts and not versions.** A *version* is immutable library content that clips pin. A *draft* is the user's unsaved source in the playground (client state, validated, never stored). A *proposal* is an agent's suggested change stored with its request: validated source, a new asset, clip edit operations or metadata, plus the base it was made against (asset version or clip revision), test frames and a thumbnail. It changes nothing until accepted; accepting turns it into a version (or a clip revision) with the note "accepted from request #n".
- **Concurrent edits.** An asset proposal made against v2 while the asset moved to v3 is a conflict on accept: the studio says so and offers "accept as v4 anyway" (nothing is lost; versions are immutable) or "ask the agent to rebase". A clip proposal is a list of edit operations plus the base revision; on accept they are re-applied to the current composition, so they rebase cleanly when the ids they touch still exist, and conflict otherwise. An editor with unsaved changes hears about a newer revision live and offers reload or keep (the revision guard refuses a blind overwrite).
- **Request lifecycle**: `open` (waiting for the agent) → `working` (claimed, with a lease and heartbeat; an expired lease returns it to open) → `review` (a pending proposal) → `done` (accepted, or completed by the agent with a reply) / `cancelled`. A user reply sends it back to `open` and supersedes the pending proposal when the next one arrives. Reject with a reason sends it back to `open`; reject without one closes it.
- **Live updates are driven by the database**: an `events` table written in the same transaction as every change (by any process); the web server tails it (cheap `PRAGMA data_version` check every 250 ms) and pushes server-sent events; the UI refreshes what it shows. The MCP process and the web server never talk directly.
- **Split keeps time**: items gained `offset` (seconds into the asset where the item starts) and `assetDuration` (the asset timeline it is cut from). `split_item` gives the second part offset = cut and both parts the whole asset duration, so the frames on both sides of a cut are identical (tested). Audio items honour the offset in the mix (`atrim=offset:offset+duration`).
- **Image layers**: a visual track takes image assets directly, drawn into the transformed box with `params.fit` contain (default), cover (cropped to the box) or fill.
- **Render in another format**: `start_render { format }` (and `renders.enqueue`) snapshot the composition reformatted, so one composition renders vertical, horizontal and square with each format's overrides; the render row records its format (`renders.format`, added by an idempotent column migration in `openDb`).
- **Run now** spawns `claude -p` with `--mcp-config` (only the studio server, on the studio's data dir), `--strict-mcp-config`, `--tools ""` (no built-in tools), `--restricted`, `--permission-mode dontAsk` and an allowlist of the studio tools that read and answer (`RUN_TOOLS`: no create/update/render tools), `--output-format stream-json`; progress lines go into the thread as `progress` messages; timeout `STUDIO_AGENT_TIMEOUT` (default 600 s), cancel, one session per request. The CLI is `STUDIO_CLAUDE_BIN` or `claude` on PATH; without it `/api/status` says `agent.runNow: false` and `POST …/run` answers 501. Tests use `test/fixtures/claude-stub.mjs`.
- **Proposal validation uses the draft's own defaults**, not the params on screen (a new version may drop a parameter); the side-by-side compare in the playground uses the user's params where they still apply.
- **Kinds, and how the runtime applies them** (all are JS function assets, versioned, pinned and traced as before):
  - `motion` returns a transform delta `{ x, y (px), scale, scaleX, scaleY, rotation (deg), opacity }` for `f.phase` in / out / emphasis / loop over `f.t`/`f.progress` of its span; attached as `item.motions[] = { asset, phase, duration, at, params }`, they stack (offsets add, scales and opacity multiply, rotations add) about the item's anchor. At rest a motion must return identity (validation warns otherwise).
  - `transition` draws `f.from` → `f.to` (full-frame layers, either may be null) over `f.progress` onto a clean layer; attached to the incoming item as `item.transition = { asset, duration, params }`. It hands over from the latest item that starts earlier on the same track; that item keeps playing during the transition, or holds its last frame if it already ended.
  - `effect` draws a processed copy of `f.source` (a full-frame layer) onto `f.ctx`; attached per item (`item.effects[]`), per track (`track.effects[]`, an adjustment layer) or per clip (`composition.effects[]`). `f.lib.fx` holds pure-JS pixel helpers (blur, glow, grain, vignette, grade, duotone, chromatic, displace, pixelate, scanlines, over); canvas `filter` is not used because Chrome and Skia-Node differ.
  - **Masks**: `item.mask = { asset (visual or image), params, mode: alpha | alpha-inverted | luma | luma-inverted, transform? }`. The mask moves with the layer unless it has its own transform.
  - **Precomps**: `f.layers(LAYERS, p)` draws clip-style layers in the asset's box; `{ $param: 'name' }` binds an exposed param. "Save as asset" (`save_precomp`) generates that source from selected items (assets named in params are pinned too), records `derivation: precomp`, and can replace the items with one item. Layer seeds differ from the clip's, so rng-driven layers can look different after replacing.
  - **Presets** are generated sources: `uses: { base: 'x@n' }`, the base's schema with the chosen values as defaults, `render(f, p) { return f.use('base', p); }`; `f.use` passes effects and transitions their layers, so presets work for every kind. `derivation: preset`, `forked_from` = the base version.
  - The playground previews a motion on a demo card, a transition between two demo scenes, an effect on a demo scene (`src/core/demo.js`); those are also the thumbnails.
  - New kinds needed a wider `CHECK (kind IN …)`: `openDb` rebuilds `asset_versions` once on old databases (foreign keys off, copy, drop, rename, triggers and indexes again, `foreign_key_check`), tested on a v1 schema. `ENGINE_VERSION` stays 1: nothing an existing asset draws changed.
- **Metadata edits are an overlay on the asset** (`assets.meta_title/description/tags`), not a version: they apply to every version and to search; null goes back to what the source declares; the source's declared values stay visible (`declared`).
- **Save as defaults** rewrites the `default:` values inside the `params` object literal in place (acorn finds the ranges), so the rest of the file is untouched; a declaration that is not an object literal is refused with "edit the source instead". New dependency: **acorn** (MIT, already in the tree through ESLint), server-side only.
- **Version diff**: Myers line diff in `src/core/diff.js`, shared by the server (`diff_versions`, with the same frame of both versions side by side) and the studio.
- **Parity is measured, not assumed**: `scripts/lib/parity.mjs` draws the same frames with the preview worker in headless Chrome and with Node, and compares them per channel. Limit: mean difference ≤ 1.5/255 and ≤ 1 % of pixels off by more than 64. Measured: mean 0.19–0.85, differences only on antialiased edges.
- **3D: a software rasterizer in `f.lib.solid`**, weighed against three.js. three.js needs WebGL; in Node that means headless-gl (native, GPU or Mesa) and in the browser a GPU path, so the two would not draw the same pixels and the render path would depend on a GPU, against the brief. `f.lib.solid` is ~450 lines of plain JS: mesh generators (icosphere, box, lathe, cylinder, torus, extrude with ear clipping, terrain with height colours, 5×7 block-letter text, instances, merge/transform/paint), a camera, ambient/directional/point lights, flat/smooth/toon shading, fog, near-plane clipping, a depth buffer and 2× supersampling, resolved to an ImageData that is drawn into the asset's box (so it composes with transforms, masks and effects like any layer). Pure arithmetic, so the 3D pixels are byte-identical in Chrome and Node (parity diff shows nothing on the 3D objects). Cost: ~70 ms for a 640×360 scene with 4.6k triangles; heavier at 1080p, which is what baking is for.
- **Baking (the user's idea, generalised)**: `bake_sequence` renders any visual asset once into a `sequence` asset (PNG frames with alpha in `files/<slug>@<v>/000000.png…`, in parallel on a full worker pool), cached by asset version + params + size + fps + duration (asking again returns the same asset, `cached: true`). A sequence is a layer like an image (`params.fit`, `params.loop`), keeps its lineage (`derivation: bake`), and its frames are loaded on demand (Node worker and preview worker each keep a small LRU) because `renderClipFrame` is synchronous. Sequences live on clip tracks and as masks, not inside precomps. `assets.type` gained `sequence` (same table-rebuild migration as the kinds).
- **Uploads** are one raw request per file (`POST /api/uploads?name=…`, `Content-Type: image/*`): not JSON, so a cross-site page cannot send one without a CORS preflight (never answered) and the Origin check refuses it anyway. The type comes from the bytes. A duplicate (same SHA-256) returns the existing asset. Each upload records size, a median-cut palette (5 colours over a 64 px copy) and a thumbnail, and waits on the needs-description list (`assets.needs_description`) until `describe_asset` sets title, description, tags and suggested uses (`assets.meta_uses`), which also makes it findable by those tags.
- **SVG safety is an allowlist rebuild**, not a blocklist: a strict XML parser (a DOCTYPE, an entity other than the five XML ones, a processing instruction or malformed markup rejects the file), then only known drawing elements and attributes are re-serialised. Dropped and reported: `<script>`, `on*` handlers, `<foreignObject>`, `<image>`, `<style>` (CSS can `@import`/`url()`), SMIL animation (it can rewrite `href`), `<a>` (contents kept), any `href`/`url()` that is not `#local`, unsafe values (`javascript:`…), style declarations outside an allowlist. The sanitised SVG is stored next to a PNG raster (≤2048 px) made once in Node; preview and render both draw that raster (browsers cannot decode SVG in a worker), so they agree.
- **`f.svg(name)`**: a vector model extracted from the sanitised SVG (paths with fills, strokes, opacities and transforms; `<use>` resolved; gradients become their first stop; text left to the raster) and drawn with plain canvas path calls by `f.lib.svg` (own path parser, arcs to Béziers, flattening for lengths): draw-on with `progress`, recolouring with `fill`/`stroke`/`colors`. Parity with Chrome: max difference 3/255.
- **Code editor: CodeMirror 6** (MIT; `codemirror` + `@codemirror/lang-javascript` and their dependencies), served by the studio from `node_modules` under `/vendor/<package>/` (an allowlist) through an import map in `index.html`: a real editor (highlighting, line numbers, search, undo, lint markers) with no build step and no CDN.
- **UI work is split by screen across four agents** with disjoint files (library; playground + code editor; clip editor; shell + live updates + ask-agent panel + requests screen). Shared files (`index.html`, `app.js`, `base.css`, `screens.css`, `lib/api.js`, `lib/util.js`, `lib/live.js`) are mine; each agent styles its screen in `src/ui/css/<area>.css`. `scripts/dev-seed-v2.mjs` gives them data with every new feature.
- **Search at scale**: one query shape for everything: the filters as `IN (subquery)` sets (computed once, not per row), the page's ids sorted first on narrow rows and their details fetched second, usage and favourites joined as aggregates. Relevance = FTS5 bm25 (slug, title, description, tags, source weighted 10/6/3/6/0.5) multiplied by quality boosts (featured, favourite, use); without a query: featured, favourites, use, newest. Facets count each value under every filter except its own (tags under all, since they narrow each other); a test checks every facet value against the total of the search it stands for. On 5,021 assets: p50 8.6 ms, p95 42 ms in-process (the HTTP measure is in `bench-library`).
- Favourites are global (the studio has one user); collections are named sets; "recently used" is updated when an asset is created, opened in the playground or put in a clip; featured is a flag. Bulk tagging is a metadata edit (no new versions).
- Filmstrips (8 frames, 240 px cells) are drawn during validation and saved next to the thumbnail; synthetic rows reuse their templates' strips.
- **Measuring compounding**: every MCP tool call is logged (`mcp_calls`: tool, author, process, ms, ok) and attributed to a clip: named in its arguments (clip, for_clip, create_clip's name, a request's clip), else the clip this author was last working on. A clip's build runs from its first call or studio request to its `start_render` call (the render is excluded); metrics: calls in that window, new lines of asset code (non-blank lines of versions made for the clip; presets and precomps the studio generated are counted apart, as generated lines), reuse share (timeline items whose pinned version was made before, for another clip), where reused items came from, build seconds and seconds per output second (`compounding_report`, `/api/compounding`).
- **The compounding levers built**: `suggest_assets(brief)` (OR-matched words ranked by bm25 × quality, a few per kind, with matched words, params, notes and a numbered contact sheet), notes agents leave on assets (`add_asset_note`, shown in `get_asset` and suggestions), real usage examples per asset from the clips that use it (`get_asset.examples`), presets and precomps (M3), featured/favourites raising proven pieces, and a clip theme: `composition.theme` pins a value asset and every asset reads it as `f.theme`, so new pieces look consistent by default.
